# Deployment

Use Node 22.13+, npm ci, npm run check and npm run build. Generic Node hosting runs npm run start; bind --hostname explicitly if your container disallows interface discovery. Vercel can use the normal Next build command. No deployment is automatically authorized by opening a repair PR.

## Client releases

Create an isolated client configuration with `npm run project:new -- client-slug recipe`, then validate it with `npm run project:validate`. `npm run project:activate -- client-slug` creates timestamped backups under `config/backups` before replacing the active configuration.

The manual `Deploy client experience` GitHub Actions workflow accepts a validated client slug, activates it inside the disposable runner, runs every check and production build, then invokes Vercel. Configure `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` as protected repository secrets. Production deployment must be deliberately selected in the workflow form.

The workflow uses the current Vercel CLI at execution time. Organizations requiring a pinned supply chain should replace `vercel@latest` with their approved version before enabling deployment.

Keep public/decoders generated by the build with the deployed assets. NEXT_PUBLIC_DEBUG_3D and NEXT_PUBLIC_FORCE_QUALITY are public presentation settings, not secrets. Actual quality remains bounded by the detected device ceiling.

For large assets prefer versioned optimized object-storage/CDN URLs. Validate MIME types, HTTPS, CORS for texture/media loading, video byte ranges, and immutable caching of content-addressed objects. Do not apply immutable caching to mutable same-name config assets. Keep critical initial bytes separate from the total asset library budget.

/api/health verifies server availability only. It does not certify WebGL, video decoding or CDN assets. Test direct page navigation, restoration, /↔/lab route identity, missing/corrupt assets, context recovery, all responsive compositions and sustained performance on actual target devices before release.
